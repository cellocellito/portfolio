## Context

When an n8n workflow fails, n8n marks the run as failed in the executions list and nothing else happens: no alert and no reason.

My n8n runs on a Hostinger VPS, and the guardian watches every workflow on it. I built it to practice and to make my own work easier.

## What I built

An error workflow. Every workflow on my n8n names it as its error workflow in its settings, so a failure reaches it through n8n's Error Trigger as soon as it happens.

A Code node keeps what matters: the workflow, the node that failed, the message and the stack, cut to 1,000 and 2,000 characters so a huge payload never lands in an alert. A second one keeps recent failures in the workflow's static data. The same workflow, node and message within 30 minutes counts as a repeat and stops there.

A new failure goes to Gemini 2.5 Flash through a structured output parser, so the answer always has the same fields: severity, category, likely cause, whether it looks transient, and a suggested fix. The alert reaches me on WhatsApp. High and critical failures open a GitHub issue first.

One of the failures it caught came from my WhatsApp assistant (A2), around its Supabase database.

## Decisions

- **Error Trigger, not polling.** A failure arrives the moment it happens, instead of waiting for a schedule to read the executions list.
- **A 30-minute window for repeats.** A workflow failing in a loop sends one alert, not one per run.
- **Gemini on the free tier.** A diagnosis is a short structured answer, and the free tier handles it with no trouble.

## What broke

Nothing I remember. I had built a guardian before, at Solutudo, so this one worked on the first build.

In use on my n8n since April 2026.
